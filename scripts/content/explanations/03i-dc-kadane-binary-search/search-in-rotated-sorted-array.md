## Задача простыми словами

Был отсортированный по возрастанию массив **различных** чисел, но его «прокрутили»: кусок из начала перенесли в конец. Например, `[0, 1, 2, 4, 5, 6, 7]` мог стать `[4, 5, 6, 7, 0, 1, 2]`. Нужно найти индекс `target` в прокрученном массиве (или `-1`) за `O(log n)`.

Пример: `nums = [4, 5, 6, 7, 0, 1, 2]`, `target = 0` → `4`; `target = 3` → `-1`.

## Наивный подход

Линейный поиск:

```ts naive
for (let i = 0; i < nums.length; i++) {
  if (nums[i] === target) return i;
}
return -1;
```

Это `O(n)` и игнорирует почти полную отсортированность. Обычный бинарный поиск «в лоб» не работает: в `[4, 5, 6, 7, 0, 1, 2]` при `target = 0` середина `7` больше `0`, и стандартный поиск ушёл бы влево — а `0` справа. Проблема в том, что сравнение с одной лишь серединой больше не говорит, куда идти.

## Ключевое наблюдение

Прокрученный массив — это два возрастающих куска:

```
[ 4  5  6  7 | 0  1  2 ]
  возрастает   возрастает
```

Если разрезать отрезок `[lo, hi]` в любой точке `mid`, **хотя бы одна** из половин `[lo, mid]` и `[mid, hi]` окажется целиком отсортированной: «излом» может попасть только в одну из них. А для отсортированной половины легко проверить, лежит ли `target` в её диапазоне, — достаточно сравнить с концами. Если лежит — ищем там, иначе — в другой половине. Каждый шаг отбрасывает половину, итого `O(log n)`.

## Техники

### Бинарный поиск с выбором отсортированной половины

**Что это.** Модификация классического бинарного поиска, где решение «влево или вправо» принимается не по одному сравнению `nums[mid]` с `target`, а в два шага: сначала определяем, какая половина упорядочена, потом проверяем, попадает ли `target` в её диапазон.

**Типичный шаблон:**

```ts naive
if (половинаСлеваОтсортирована) {
  if (target в [nums[lo], nums[mid])) идтиВлево;
  else идтиВправо;
} else {
  if (target в (nums[mid], nums[hi]]) идтиВправо;
  else идтиВлево;
}
```

**Когда применять.** Данные «почти отсортированы»: прокрутка, склейка двух отсортированных кусков. Подробнее о бинарном поиске — во вкладке «Теория».

**Как применяется здесь.** Признак «левая половина отсортирована» — `nums[lo] <= nums[mid]`: в прокрученном массиве из различных чисел это возможно, только если излома между `lo` и `mid` нет.

### Закрытый интервал `[lo, hi]`

Используется классическая форма: `while (lo <= hi)`, `mid` проверяется на равенство и затем исключается сдвигом `mid ± 1`. Цикл заканчивается, когда отрезок пуст.

## Разбор кода

```ts
function search(nums: number[], target: number): number {
  let lo = 0;
  let hi = nums.length - 1;
```

Отрезок поиска — весь массив, закрытый интервал.

```ts
  while (lo <= hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (nums[mid] === target) return mid;
```

Берём середину и сначала проверяем самое простое — не она ли ответ. Дальше `mid` можно исключать из поиска.

```ts
    // Хотя бы одна из половин [lo, mid] или [mid, hi] отсортирована
    if (nums[lo] <= nums[mid]) {
      // Левая половина отсортирована: проверяем, попадает ли target в её диапазон
      if (nums[lo] <= target && target < nums[mid]) {
        hi = mid - 1;
      } else {
        lo = mid + 1;
      }
```

`nums[lo] <= nums[mid]` — левая половина `[lo, mid]` возрастает. Именно `<=`, а не `<`: когда `lo === mid` (в отрезке 1–2 элемента), «половина» из одного элемента тоже отсортирована. Диапазон этой половины — от `nums[lo]` до `nums[mid]`. Правая граница строгая (`target < nums[mid]`), потому что равенство с `nums[mid]` уже проверено. Если `target` в диапазоне — он может быть только слева (`hi = mid - 1`); иначе слева его точно нет, идём вправо.

```ts
    } else {
      // Правая половина отсортирована
      if (nums[mid] < target && target <= nums[hi]) {
        lo = mid + 1;
      } else {
        hi = mid - 1;
      }
    }
  }
```

Иначе излом лежит в левой половине, а значит, правая `[mid, hi]` отсортирована. Проверяем диапазон `(nums[mid], nums[hi]]` — здесь строгая левая граница, по той же причине. Попадает — идём вправо, нет — влево.

```ts
  return -1;
}
```

Отрезок опустел — `target` в массиве нет.

## Трассировка

`nums = [4, 5, 6, 7, 0, 1, 2]`, `target = 0`:

1. `lo = 0`, `hi = 6`, `mid = 3`, `nums[3] = 7 ≠ 0`. `nums[0] = 4 <= 7` — левая отсортирована. `4 <= 0`? Нет → `target` не слева, `lo = 4`.
2. `lo = 4`, `hi = 6`, `mid = 5`, `nums[5] = 1 ≠ 0`. `nums[4] = 0 <= 1` — левая `[0, 1]` отсортирована. `0 <= 0 && 0 < 1` — да → `hi = 4`.
3. `lo = hi = 4`, `mid = 4`, `nums[4] = 0` — возвращаем `4`.

`target = 3`:

1. `mid = 3` (`7`): левая отсортирована, `4 <= 3` нет → `lo = 4`.
2. `mid = 5` (`1`): левая `[0, 1]` отсортирована, `3 < 1` нет → `lo = 6`.
3. `mid = 6` (`2`): `nums[6] <= nums[6]`, левая из одного элемента, `3 < 2` нет → `lo = 7`.
4. `lo = 7 > hi = 6` — ответ `-1`.

Почему важно `<=`: для `nums = [3, 1]`, `target = 1` на первом шаге `lo = mid = 0`. С `<=` левая половина `[3]` считается отсортированной, `1` в неё не попадает → `lo = 1`, и следующий шаг находит `1`. Со строгим `<` код решил бы, что отсортирована правая половина, проверил `3 < 1` — ложь — и ушёл бы в `hi = -1`, вернув `-1`.

## Почему это работает

Инвариант: если `target` есть в массиве, его индекс лежит в `[lo, hi]`.

На каждом шаге одна из половин отсортирована (в отрезке не более одного излома, и он не может попасть сразу в обе половины, кроме общей точки `mid`). Для отсортированной половины все её значения лежат между её концами, так что проверка «попадает ли `target` в диапазон» точна в одну сторону: если не попадает — в этой половине его заведомо нет, и отбрасывать её безопасно. Если попадает — переходим в эту половину; отбросить другую тоже безопасно: если `target` вообще есть в массиве, а в отсортированной половине его значение «помещается», то другая половина, состоящая из значений вне этого диапазона (весь массив — один прокрученный возрастающий цикл без повторов), его содержать не может. Отрезок строго сокращается (`mid` исключается), поэтому цикл конечен.

## Пограничные случаи

- **Массив не прокручен** (`[1, 2, 3, 4, 5]`): всегда срабатывает ветка «левая отсортирована», получается обычный бинарный поиск.
- **Один элемент**: одна проверка на равенство, иначе `-1`.
- **Два элемента** (`[3, 1]`): решающую роль играет `<=` в `nums[lo] <= nums[mid]`.
- **`target` — минимум или максимум** (на изломе): обрабатывается проверками диапазонов.
- **`target` вне всех значений**: отрезок сжимается до пустого, `-1`.

## Сложность

- **Время `O(log n)`**: каждая итерация исключает `mid` и одну из половин.
- **Память `O(1)`**: только индексы.

## Типичные ошибки

1. **`nums[lo] < nums[mid]` вместо `<=`** → ломается при `lo === mid`, пример `[3, 1]`, `target = 1`.
2. **Неполная проверка диапазона**: написать только `target < nums[mid]` без `nums[lo] <= target` → `target`, меньший всей левой половины (он лежит справа, за изломом), ошибочно ищется слева.
3. **Сравнивать `target` только с `nums[mid]`**, как в обычном поиске → уходим не в ту половину.
4. **Применить к массиву с дубликатами**: при `nums[lo] === nums[mid] === nums[hi]` нельзя понять, какая половина отсортирована (это задача II, там худший случай `O(n)`).
5. **`while (lo < hi)` при закрытом интервале** → последний кандидат не проверяется.

## Как узнать такую задачу

- «Отсортированный массив, сдвинутый/прокрученный в неизвестной точке» + требование `O(log n)`.
- Данные состоят из двух отсортированных кусков — ищите, какая половина «чистая».
- Альтернатива — сначала найти точку сдвига (Find Minimum in Rotated Sorted Array), потом обычный бинарный поиск в нужном куске.
- Родственные задачи: Find Minimum in Rotated Sorted Array, Search in Rotated Sorted Array II, Find Peak Element.
