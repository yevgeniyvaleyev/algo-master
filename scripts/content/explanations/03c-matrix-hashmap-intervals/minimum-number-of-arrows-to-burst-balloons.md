## Задача простыми словами

Каждый шар — отрезок `[x_start, x_end]` на оси `x`. Стрела, выпущенная вертикально в точке `x`, лопает все шары, для которых `x_start <= x <= x_end`. Нужно найти **минимальное число стрел**, чтобы лопнуть все шары. Иначе говоря — минимальное число точек, таких что каждый отрезок содержит хотя бы одну из них.

Пример: `[[10,16],[2,8],[1,6],[7,12]]` → `2`. Стрела в `x = 6` лопает `[1,6]` и `[2,8]`, стрела в `x = 11` (или `12`) — `[7,12]` и `[10,16]`.

## Наивный подход

Можно перебирать «кандидатов» для стрел: оптимальную стрелу всегда можно сдвинуть вправо до конца какого-то шара, поэтому кандидаты — концы шаров. Дальше — перебор подмножеств кандидатов или жадность «стрелять туда, где лопнет больше всего шаров», с пересчётом после каждого выстрела:

```ts naive
let left = [...points];
let arrows = 0;
while (left.length > 0) {
  // точка, покрывающая больше всего оставшихся шаров
  let bestX = left[0][1], bestCnt = 0;
  for (const [, x] of left) {
    const cnt = left.filter(([s, e]) => s <= x && x <= e).length;
    if (cnt > bestCnt) { bestCnt = cnt; bestX = x; }
  }
  left = left.filter(([s, e]) => !(s <= bestX && bestX <= e));
  arrows++;
}
```

Это `O(n³)` в худшем случае, и, что хуже, жадность «по максимальному покрытию» **не гарантирует** оптимум в общем случае. Лишнее здесь — мы каждый раз смотрим на все шары без порядка, хотя если упорядочить шары, становится ясно, куда ставить каждую стрелу.

## Ключевое наблюдение

Посмотрим на шар, который **кончается раньше всех**. Его обязательно надо лопнуть какой-то стрелой, и эта стрела стоит не правее его конца `x_end`. Сдвинем её вправо **ровно в `x_end`**: шары, которые она лопала левее, она по-прежнему лопает (все они кончаются не раньше `x_end` и начинаются не позже прежней точки), а новых может только прибавиться.

Значит, после сортировки по концу жадная стратегия «стрела — в конец первого не лопнувшего шара» оптимальна, и всё решается одним проходом.

## Техники

### Жадный алгоритм на интервалах (сортировка по концу)

**Что это.** Жадность — на каждом шаге делаем локально лучший выбор и никогда его не пересматриваем. Чтобы ей верить, нужен аргумент «обмена»: любое оптимальное решение можно перестроить так, чтобы оно начиналось с нашего жадного выбора, не ухудшив ответ.

**Типичный шаблон для интервалов.** Сортировка **по концу** + один проход: берём интервал, который кончается раньше всех, принимаем решение в его правой границе, пропускаем всех, кого это решение «покрыло». Так решаются задачи о минимальном числе точек, покрывающих отрезки, и о максимальном числе непересекающихся отрезков (Activity Selection).

**Как применяется здесь.** Стрела ставится в конец первого не лопнувшего шара; шары, начинающиеся не правее неё, считаются лопнувшими. Подробнее об интервалах и жадных стратегиях — во вкладке «Теория».

### Почему по концу, а не по началу

При сортировке по началу первый шар может оказаться очень длинным, и стрела в его конце пропустит короткие шары внутри. Тогда приходится «сужать» точку стрелы: `arrowX = min(arrowX, end)`. Сортировка по концу избавляет от этого: следующий шар кончается не раньше стрелы, поэтому достаточно проверить только его начало.

## Разбор кода

```ts
function findMinArrowShots(points: number[][]): number {
  // Сортируем по КОНЦУ шара.
  // В JS числа — double, поэтому a[1] - b[1] не переполняется (в Java/C++ это ловушка)
  points.sort((a, b) => a[1] - b[1]);
```

Сортируем шары по правой границе. Координаты доходят до `±2^31`, и разность двух таких чисел не помещается в 32-битный `int` — в Java/C++ компаратор `a[1] - b[1]` сломался бы. В JS все числа — 64-битные `double`, разность до `2^32` представляется точно.

```ts
  let arrows = 1;
  // Первая стрела — в самый правый край шара, который кончается раньше всех
  let arrowX = points[0][1];
```

По условию шаров хотя бы один, так что минимум одна стрела нужна. Ставим её в конец самого «раннего» шара — по ключевому наблюдению это оптимально.

```ts
  for (let i = 1; i < points.length; i++) {
    const [start, end] = points[i];
    // Шар начинается правее текущей стрелы — она его не задевает, нужна новая
    if (start > arrowX) {
      arrows++;
      arrowX = end;
    }
    // Иначе start <= arrowX <= end (концы отсортированы) — шар уже лопнул
  }

  return arrows;
}
```

Идём по шарам в порядке концов. Текущая стрела `arrowX` — конец некоторого более раннего шара, поэтому `arrowX <= end` для текущего шара гарантированно. Остаётся проверить начало:

- `start > arrowX` — шар целиком правее стрелы, она его не задела. Нужна новая стрела, и снова жадно: в конец **этого** шара (он кончается раньше всех ещё не лопнувших).
- `start <= arrowX` — значит, `start <= arrowX <= end`, стрела проходит через шар, он уже лопнул. Ничего не делаем.

Сравнение строгое (`>`): шары `[1,2]` и `[2,3]` лопаются одной стрелой в `x = 2`.

## Трассировка

Пример 1: `points = [[10,16],[2,8],[1,6],[7,12]]`.

После сортировки по концу: `[[1,6],[2,8],[7,12],[10,16]]`.

```
|----|            [1,6]
 |-----|          [2,8]
      |----|      [7,12]
         |-----|  [10,16]
     ^     ^      стрелы в x=6 и x=12
```

1. Старт: `arrows = 1`, `arrowX = 6`.
2. `i = 1`, `[2,8]`: `2 > 6`? Нет → лопнул стрелой в `6`.
3. `i = 2`, `[7,12]`: `7 > 6`? Да → `arrows = 2`, `arrowX = 12`.
4. `i = 3`, `[10,16]`: `10 > 12`? Нет → лопнул стрелой в `12`.

Ответ `2`.

Пример 3: `points = [[1,2],[2,3],[3,4],[4,5]]` (уже отсортирован по концу).

1. `arrows = 1`, `arrowX = 2`.
2. `[2,3]`: `2 > 2`? Нет → лопнул (касание в точке 2).
3. `[3,4]`: `3 > 2`? Да → `arrows = 2`, `arrowX = 4`.
4. `[4,5]`: `4 > 4`? Нет → лопнул.

Ответ `2`. В примере 2 (`[[1,2],[3,4],[5,6],[7,8]]`) каждое начало больше предыдущего конца, и каждый шар требует своей стрелы — ответ `4`.

## Почему это работает

**Аргумент обмена.** Пусть `b` — шар с наименьшим концом `e`. Любое решение содержит стрелу `x`, лопающую `b`, то есть `x <= e`. Заменим её на стрелу в `e`. Каждый шар `[s, t]`, который лопала `x`, имеет `s <= x <= e` и `t >= e` (концы всех шаров `>= e`), значит, стрела в `e` его тоже лопает. Число стрел не изменилось — существует оптимальное решение со стрелой в `e`.

**Индукция.** После выстрела в `e` лопнули ровно шары с `start <= e` (их концы `>= e`). Оставшиеся шары — те, у кого `start > e`; для них задача та же, и снова оптимально стрелять в конец самого раннего из них. Цикл делает ровно это: пропускает шары с `start <= arrowX` и ставит новую стрелу в конец первого шара с `start > arrowX`. Шары, пропущенные дальше по ходу, тоже лопнули, потому что `start <= arrowX <= end`.

## Пограничные случаи

- **Один шар**: цикл не выполняется, ответ `1`.
- **Касание** (`[1,2]` и `[2,3]`): строгое `>` даёт одну стрелу.
- **Вложенные шары** (`[1,10]` и `[3,4]`): после сортировки `[3,4]` первый, стрела в `4` лопает и `[1,10]`.
- **Огромные координаты** (`-2^31` и `2^31 - 1`): разность в компараторе точна в JS.
- **Все шары перекрываются в одной точке**: одна стрела.
- **Ни один шар не пересекается**: по стреле на шар.

## Сложность

- **Время `O(n log n)`**: сортировка; проход — `O(n)`.
- **Память `O(1)`** дополнительно (не считая памяти самой сортировки): две переменные.

## Типичные ошибки

1. **Сортировать по началу без сужения `arrowX`** → стрела в конце длинного шара пропускает короткие внутри (`[[1,10],[2,3],[4,5]]` даёт `1` вместо `2`).
2. **`>=` вместо `>`** → касающиеся шары получают лишнюю стрелу.
3. **Начинать с `arrows = 0`** и забыть первую стрелу.
4. **Переполнение в компараторе** при переносе решения на Java/C++ — там нужен `Integer.compare`.
5. **Пытаться сливать шары как в Merge Intervals** (объединение, а не пересечение) → группа «лопается одной стрелой» только если у всех шаров есть **общая** точка, а объединение этого не гарантирует.

## Как узнать такую задачу

- Нужно **минимальное число точек**, чтобы каждый отрезок содержал хотя бы одну, — или эквивалентно, максимальное число попарно непересекающихся отрезков.
- Формулировки «минимум выстрелов / проверок / остановок, покрывающих все интервалы» → жадность с сортировкой по концу.
- Родственные задачи: Non-overlapping Intervals (ответ = `n` − число стрел по той же схеме со строгим пересечением), Merge Intervals, Meeting Rooms, Activity Selection.
