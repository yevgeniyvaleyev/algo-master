@AGENTS.md

## Project

AlgoMaster is a personal Android-only app (Expo SDK 57, Expo Router, TypeScript) for **refreshing** LeetCode "Top Interview 150" algorithms. The user reads the material and marks an algorithm as learned; there is no code input. A daily quota (`dailyGoal`) is planned to gate entertainment apps: each learned algorithm unlocks `minutesPerAlgo` minutes, and meeting the goal unblocks everything. There is no auth or backend. The UI language is Russian. The full roadmap is in `docs/ROADMAP.md` (phase 4 is the scraper and real content, phase 5 is native app blocking).

## Commands

```bash
npm test                      # jest (jest-expo preset); tests live in src/**/__tests__/*-test.ts
npx jest src/logic/__tests__/progress-test.ts -t streak   # single file / test name
npm run typecheck             # tsc --noEmit
npm run lint                  # expo lint
npm run format                # prettier (singleQuote, printWidth 120)
npx expo export --platform android   # quick JS bundle check without a native build
npm run android               # expo run:android — native dev build (needs JDK 17+, see below)

# content pipeline (phase 4)
npm run scrape                # LeetCode GraphQL -> scripts/out/{plan.json,problems/*.json} (resumable, --force to refetch)
npm run content:sync          # scraped data -> data/algos/*.json, data/manifest.json, data/content-index.ts
npm run content:validate      # zod schema + Russian text checks + tsc on every solutionTs
npm run content:explain scripts/content/explanations/<batch>   # merge «Разбор» walkthroughs (<slug>.md files) as explanationRuMd
npm run icons                 # regenerate app/adaptive/notification icons in assets/ (scripts/icons/generate.mjs)
npm run content:images        # download content images -> data/images + data/image-index.ts (offline; MarkdownView uses them)
node scripts/content/apply.mjs scripts/content/generated/<batch>.mjs  # run a batch's tests, merge passing content into data/
```

The scraper uses Playwright's `request` API against `https://leetcode.com/graphql`, because the HTML pages are behind a Cloudflare bot check. Playwright 1.64 can't download browsers on macOS 12, so if a browser is ever needed, use `channel: 'chrome'`.

The system default Java is 9, which is too old. Native builds need `JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"`. `android/` is generated by `expo prebuild` and gitignored, so configure native behavior through `app.json` and config plugins.

## Architecture

- **Two data sources.** Read-only algorithm content is bundled JSON (`data/algos/<slug>.json`, `data/theory/<key>.json`, typed by `src/content/types.ts`). Metro needs static `require`s, so it is loaded through the lazy loader map in `data/content-index.ts`. User-mutable state lives in SQLite (`src/db/client.ts` holds the schema and migrations via `PRAGMA user_version`; `src/db/repo.ts` holds all queries). Write transactions go through `writeTransaction` (expo-sqlite runs exclusive transactions on their own connection; it sets a busy timeout so concurrent writes wait instead of failing with "database is locked"). Settings → «Сбросить все данные» only sets kv `resetPending`; `migrate` drops every table on the next start, before anything else runs.
- **Seeding.** `data/manifest.json` (topics + algos + `seedVersion`) is upserted into SQLite on startup by `runSeed`. The pure diff is `planSeed` in `src/logic/seed.ts`. Bump `seedVersion` whenever the manifest changes. Re-seeding never overrides the user's topic renames, algorithm moves or progress. Seeded topics the user deleted are remembered in kv `deletedSeedTopics` and not recreated. The built-in `__uncategorized__` ("Без темы") topic receives algorithms from deleted topics and cannot be deleted.
- **Progress semantics.** `progress` holds the current learned mark. `learn_log` is the history that drives the daily quota, streak and charts (`COUNT(DISTINCT slug)` per local `day`). Unmarking also deletes _today's_ log rows for that slug, so the quota can't be gamed, and its `cards` row (back to «не изучены»; learned again, it starts in «ждут»). Marks never expire (auto-unmark was removed with DB v10, which also dropped orphaned `cards` rows): forgetting is handled by the flash-card boxes. **Days** are the app's days, not calendar days: `dayKey()` (`src/logic/dates.ts`) shifts by the setting `dayStartHour` («Новый день с», 0–6, default 0; module state set by the settings store), so marks before that hour count for the previous day. Code that builds "hour X of today" uses `logicalDay()` (`atHour`, `planReminders`, forecast); a date that already is a day uses `calendarKey()`. The reminder window can't start before it, and the native blocker/alarms get `dayStartHour` in their configs and shift their `today()` the same way. Stored day keys are never recomputed. An algorithm can also be _in progress_ (table `in_progress`, DB v6): the algorithm header toggle cycles not learned → in progress → learned → not learned (`nextStatus`/`algoStatus` in `src/logic/progress.ts`, `setStatus` action); learning or unmarking clears it, and it never counts toward the quota. The dashboard's «В процессе» card lists them (newest first) and the list shows them with an orange clock.
- **Reactivity.** There is no query library. Mutations go through `src/logic/actions.ts`, which bumps `useDataVersion`. `useQuery(fn, key)` (`src/hooks/use-query.ts`) re-runs on screen focus and on every bump. Call mutations from `actions`, not directly from `repo`, or screens won't refresh. `useQuery` only runs inside a navigator screen (it uses `useFocusEffect`); components that can render outside one, like the card gate's `FlashCard`, use `useLiveQuery` (same file: mount, key change and every bump).
- **Settings** are a zustand store (`src/store/settings.ts`) persisted as one JSON blob in the `kv` table. The theme is applied through `Appearance.setColorScheme`, so `useColorScheme()` / `useColors()` (`src/theme`) reflect both the override and automatic system switching. Everything outside React follows it explicitly too: the root layout renders `<NavigationBar style>` (`expo-navigation-bar`, plugin `enforceContrast: false` so Android draws no light scrim) and calls `SystemUI.setBackgroundColorAsync(colors.background)`; the tab bar gets `colors.surface` via `screenOptions`.
- **Navigation.** expo-router ships its own fork of react-navigation, so don't install `@react-navigation/*` packages. Use `expo-router/js-tabs` (bottom tabs in `src/app/(tabs)`) and `expo-router/js-top-tabs` (the 7 content tabs in `src/app/algo/[slug]/`; tab screens read `slug` via `useAlgoContent`).
- **Algorithm screen tabs** get the slug from `AlgoSlugContext` (`useAlgoSlug` / `useAlgoContent`), provided by `algo/[slug]/_layout.tsx`, because top-tab screens don't reliably receive the parent's `[slug]` param.
- **Learning order.** Suggestions (`getNextUnlearned`) follow `learningOrder` (`src/logic/learning-order.ts`): topics take turns round-robin, each giving its easiest remaining unlearned algorithm (easy → medium → hard), starting with the topic after the one most recently learned (latest `learn_log` row).
- **Search.** The Algorithms list has a search field: `matchesQuery` (`src/logic/search.ts`, pure, tested) splits the query on whitespace/dots; numeric tokens match the LeetCode number by prefix, others a substring of the title or slug. While searching, matches show even in collapsed topics (collapse state untouched), empty topics are hidden, and the «Не изучены» filter still applies. A chevron chip next to «Отметить» collapses every topic while any is open, otherwise expands them all (writes `collapsedTopics` for each topic; hidden while searching).
- **Marking from the list** only happens in bulk mode (the «Отметить» chip, then Save/Cancel via `setLearnedMany`), so a stray tap can't change stats.
- **Reminders.** Local notifications (`expo-notifications`, works in Expo Go). `planReminders` (`src/logic/reminders.ts`, pure, tested) produces date triggers every `reminderIntervalHours` between `reminderStartHour` and `reminderEndHour`: today's remaining slots only while the goal isn't met, plus 7 days ahead. `syncReminders` (`src/notifications/reminders.ts`) cancels all and reschedules. It runs on startup, on foreground, after marking (`actions`) and on reminder/goal setting changes (a `useSettings.subscribe` in the root layout); calls are serialized. Vibration is the setting `reminderVibration` (patterns in `src/logic/vibration.ts`, pure, tested; Settings → «Вибрация» previews with RN `Vibration`). Android can't change a channel's vibration after creating it, so each type has its own channel (`channelId`: `reminders` for «Как в системе», else `reminders-<key>`) and `ensureChannel` deletes the others.
- **App blocking (phase 5).** Local Expo module `modules/app-blocker` (Kotlin, Android-only, autolinked; its manifest declares the AccessibilityService, `BlockActivity` and a launcher `<queries>`, so no config plugin is needed). JS pushes `{enabled, blockedPackages, dailyGoal, learnedToday, grantedMs, deadlineMs, reserveMs, day}` via `syncBlocker` (`src/blocker/sync.ts`) into SharedPreferences (`BlockerStore`). `BlockerService` tracks time in blocked apps (paused while the screen is off) and shows `BlockActivity` once `min(granted − used, deadline − now − reserve)` runs out; nothing is blocked after the goal is met. `AppBlocker` is `null` in Expo Go (`requireOptionalNativeModule`). Reminders and blocker are re-synced together by `syncBackground` (`src/logic/background.ts`) on startup, foreground, marking, and changes to `BACKGROUND_SETTING_KEYS`. Native changes need a new build (EAS: `eas.json` profiles `development` / `preview`, both APK).
- **Adaptive budget.** Entertainment time is planned in JS (`src/logic/budget.ts`, pure, tested; loaded by `loadDayBudget` in `src/logic/day-budget.ts`). The learning day is the reminder window (`reminderStartHour`–`reminderEndHour`, the end is the goal deadline). Each planned item reserves its time: a new algorithm `learnMinutes × difficultyFactors[difficulty]` (next ones in suggestion order), a review `cardMinutes`; slack = time to deadline − reserve. Each success today (learned algorithm or card answered ✓, oldest first) grants `clamp(slack / (left + 1), 0, cap)` with `cap = minutesPerAlgo × its cost / learnMinutes` (so a card earns proportionally less), recomputed on every sync; the spendable balance is also capped by the live slack. The dashboard's «Учебный день» card (`DayTimeline`, laid out by `dayTimeline`) visualizes it.
- **Study plan and alarms.** `planDay` (`src/logic/study-plan.ts`, pure, tested) splits the rest of the learning day into one interval per remaining algorithm and centres each algorithm's learning time in it (proportional intervals if a block doesn't fit an equal share, packed from now if nothing fits). The dashboard timeline draws this plan. Local module `modules/study-alarms` (Kotlin, autolinked, `null` in Expo Go) gets the plan _inputs_ from `syncAlarms` (`src/alarms/sync.ts`, part of `syncBackground`) and plans natively: `StudyPlan.kt` mirrors `planDay`/`nextAlarmAt` (keep them in sync). One exact `setAlarmClock` alarm is kept for the next block start (≥ `MIN_ALARM_GAP_MS` from now; tomorrow once today is done). When it fires, `AlarmReceiver` shows an insistent full-screen notification (`AlarmActivity`, «Начать» deep-links to `algomaster://algo/<slug>`) and immediately re-plans from now, so an ignored alarm needs no detection. Boot/time changes re-plan via `RescheduleReceiver`. Algorithm and card-group alarms have separate switches (`alarmsEnabled` → config `enabled`, `cardAlarmsEnabled` → `cardsEnabled`): every block is still planned, and the alarm rings at the first block whose kind is on (`nextAlarmAt(plan, now, rings)` / `StudyPlan.firstRinging`; the dashboard's bells follow `dayTimeline`'s `rings`). Card alarms get their own screen in `AlarmActivity` (✓ today of `cardDailyGoal`, `cardsDue`, `cardsDueByBox`, all pushed by `syncAlarms`). «Отложить на N мин» (`alarmSnoozeMinutes`) sets a second alarm (`AlarmScheduler.snooze`, extra `snoozed`) that re-rings the same block only if it's still to do (`stillToDo`); «Пропустить» just closes. Settings «Проверить» tests either kind (`testAlarm('algo' | 'cards')`). In dev mode (`__DEV__`, so also Expo Go) Settings → «Для разработки» opens `/alarm-preview?kind=algo|cards|reminder` (`src/app/alarm-preview.tsx`, transparent modal): a JS copy of the alarm screen / a mock heads-up reminder from the real day plan, with the chosen vibration (RN `Vibration`), scheduling nothing. Its texts come from `alarmScreen` (`src/logic/alarm-screen.ts`, pure, tested; mirrors `AlarmNotification.texts`/`AlarmActivity`, keep in sync) and `reminderContent` (`src/logic/reminders.ts`, also used by the real reminders). The alarm vibration is played natively by `AlarmRinger` (not the channel, which has vibration off), so it can repeat as set: `alarmWaveform(pattern, alarmVibrationRepeat, alarmVibrationTimes)` (`src/logic/vibration.ts`, pure, tested: once / N times / looping / looping with a 5 s pause; timings alternate wait/vibrate by position, so N cycles are joined after their leading wait) goes to the config as `vibration` timings + `vibrationRepeat` loop index. The sound (`alarmSound`: '' default alarm, 'silent', or a ringtone URI from `getAlarmSounds`; title in `alarmSoundTitle`) is the channel's, repeated by FLAG_INSISTENT; since a channel's sound is fixed, `AlarmNotification` uses channel `study-alarms-<soundId>` and deletes the other `study-alarms*` channels. Every way out stops the ring via `AlarmRinger.stop` (notification + vibration + the one-minute `ACTION_STOP` timeout alarm): the screen's buttons/back, the notification's actions (its «Начать» goes through `AlarmActivity` `ACTION_START`, no UI), swipe (`deleteIntent`). Settings → «Мелодия» (`SoundPickerModal`) previews sounds natively (`previewSound`/`stopSoundPreview`, 5 s).
- **Flash cards.** Every algorithm is a card in one pipeline: «не изучены» (no `progress` row; `getUnlearned`/`getUnlearnedCount`, a view only: learning still happens from the list, dashboard and alarms) → «ждут» → boxes 1–5. The «Карточки» tab (`src/app/(tabs)/cards.tsx`) reviews _learned_ algorithms with the Leitner method (`src/logic/leitner.ts`, pure, tested). Learned algorithms without a `cards` row (DB v4) wait outside the box; box 1 holds `cardBoxOneSize` cards that rotate in the session: ✓ sends a card to box 2 and the longest-waiting card (oldest `learned_at`, ties by LeetCode number) refills box 1, ✗ moves it to the end of the rotation; the ‹ › arrows at the edges browse the queue as a circle without answering (`browse`, no writes). Boxes 2–5 are date-based (`BOX_INTERVAL_DAYS[box − 1] × cardIntervalFactor` = 3/7/14/30 days; box 5 stays in box 5) and come before the rotation; ✗ there drops the card into box 1. `startSession`/`answer` are pure and return `CardWrite`s persisted by `saveCardWrites`; the screen builds the session from the DB on focus only, so its own saves don't reshuffle it. `learned_at` stays the time it was learned (the «ждут» order); ✗ never touches marks, the quota or `learn_log`. Each ✓ is also logged in `card_log` (DB v5; the migration backfills the last ✓ of cards already in boxes 2–5) for the history and the dashboard's «Карточки» card: refreshed today / ever (`getCardRefreshStats`, distinct algorithms), `dueCount`, and the pile sizes (`CardBoxes`, shared with the cards tab; `unlearned` adds a first «не изуч.» cell (dashboard and cards tab, not the gate); boxes 2–5 with cards due read «10/3», the due count from `dueByBox` smaller and in orange; where `active` highlights the current card's box in `primary`/`onPrimary`; the card header also shows the box as a chip (box icon + number) and a bulb icon button that opens `/algo/<slug>` (badges and buttons are a fixed right-aligned group; a long title wraps beside them); returning from it keeps the session via the `resumeOnFocus` ref, so that one focus doesn't rebuild). The front is the original English condition (`conditionMd`, `MarkdownView compact`), the back the own solution if any, else the bundled one (`CodeViewer compact`; a «1 / 2» (own / bundled) toggle in the header row when both exist; on that side the difficulty shrinks to E/M/H and the box chip to a bare number); only the icon button between ✕ and ✓ flips the card, so its content scrolls freely. The tab badge is `dueCount`.
- **Card statistics.** The chart icon in the «Карточки» tab header opens `/card-stats` (`src/app/card-stats.tsx`): summary tiles (pending, today ✓/✗ answers, accuracy, refreshed today/ever), the piles (`CardPiles`: «не изуч.», «ждут» and boxes 1–5 as `DifficultyRing`s, a donut split Easy/Medium/Hard by `difficultyByPile` with the count inside, the non-zero Easy/Medium/Hard counts under it in their colors and «/N» due under boxes 2–5; tapping one filters the list to that pile and scrolls there, tapping it again shows all), distinct ✓ cards per day for 14 days (`DailyBars`, goal `cardDailyGoal`) and every algorithm with its box, due state and ✓/✗ counts (unlearned ones read «не изучено» / «изучаю» and sort last), filtered (К повтору / Не изучены / Ждут / box 1–5 / Все) and sorted (По сроку / Сложные / Номер). `buildCardStats`/`filterRows`/`sortRows`/`dueLabel` are pure in `src/logic/card-stats.ts` (tested); answer counts come from `card_reviews` (`getCardReviewTotals`, only since DB v7), «Обновлено» from `card_log`.
- **Daily goal.** One «Цель в день» (`dailyGoal`, default 8; `migrateGoal` in `src/logic/goal-migration.ts`, tested, turned the old «Алгоритмов в день» + «Карточек в день» into their sum, `goalVersion: 2`): successful cards. Every distinct card answered ✓ today (gate included, also after an ✗) and every algorithm learned today counts once (`getCardDayStats` / `getTodayLearned`; per day `getDailySuccess`, the union of `learn_log` and `card_reviews` known = 1, for the streak, the dashboard bars and the history header). ✗ answers only pass the entry gate. What is left is taken in priority order by `studyDay` (`src/logic/card-day.ts`, pure, tested): the reviews pending today (`pendingSlugs`: due boxes 2–5, the box-1 rotation and the «ждут» cards refilling it) up to the goal (`cards`), then new algorithms from «не изучены» (`algos`). Algorithms learned today stay in «ждут» until the next day (`waiting()` in `leitner.ts` skips them), so a fresh one isn't reviewed right away. Pulling cards ahead was dropped (`card_reviews.ahead` stays 0). Recomputed on every load; running out of everything counts as done. When the reviews run out with `algos > 0`, the cards tab shows a «Новый алгоритм» card (next in learning order, «Изучить» opens it). `loadStudyDay`/`loadDayBudget` (`src/logic/day-budget.ts`) feed it into the day: `planItems(next.slice(0, algos), cards, cardCost)` (StudyPlan.kt mirrors it), `goalMet` = nothing left (unlocks the blocker, stops today's reminders). The native configs keep their fields: `goal`/`dailyGoal` = learned today + `algos`, `cardsLeft` = `cards`, and tomorrow's fallback from `splitTomorrow` (`cardGoal` = tomorrow's pending reviews, `goalTomorrow` = the rest as new algorithms). Card answers re-sync the background after a 2 s debounce.
- **Credit («Взять в долг», issue #3).** While something of today's goal is left and no debt is open, the dashboard's «Сегодня» card offers «Взять в долг» (`CreditModal`: how much of the goal, repaid over 1 or 2 days). Table `credits` (DB v9, append-only: day, algos, cards, days; new rows store the amount in `cards`, older ones are added together, `creditAmount`); repayment is computed, never stored: `creditState`/`creditPart` (`src/logic/credit.ts`, pure, tested) on the daily successes — the credit day's goal shrinks by the amount (it counts as met, streak and history included via `borrowedByDay`), the next days get installments (`ceil(n/days)`, then the rest), only work above a day's own goal repays (the credit day's reduced goal included), and an unpaid installment stays due every following day until repaid. One credit per day, a new one only once the last is repaid (`canTakeCredit`). `loadCredit` feeds the effective goal into `studyDay` and so into the plan, blocker, alarms and reminders (`planReminders` takes tomorrow's goal). The dashboard shows «Долг: N карт. — до <день>» (`creditLine`).
- **Card gate.** «Карточки при входе» (`cardGateCount`, 0 = off and the default; `migrateSettings` turned it off once for existing installs, `gateVersion: 2`): `CardGate` (`src/components/CardGate.tsx`) covers the whole app until that many cards are answered (✓ or ✗, real Leitner reviews; no browse arrows, no bulb, hardware back swallowed). The root layout opens it on a cold start and after `GATE_AWAY_MS` (10 min) in the background (`shouldGate` in `src/logic/card-gate.ts`, pure, tested), skips it for algorithm deep links (`isAlgoLink`, the alarm's «Начать»), and keeps the count in memory (`useCardGate`). The review UI (`CardReview` in `src/components/CardReview.tsx`) is shared with the «Карточки» tab.
- **Backup.** Settings → «Резервная копия». A backup is a JSON snapshot of every user table (`createSnapshot` in `src/backup/backup.ts`; format, validation, summary, column intersection and file rotation are pure in `src/logic/backup.ts`, tested). «Сохранить копию» writes `algomaster-YYYY-MM-DD.json` into a folder picked with `Directory.pickDirectoryAsync` (expo-file-system, Android SAF; the permission persists). «Восстановить из файла» (`File.pickFileAsync` → `parseBackup`, rejects foreign files and newer `dbVersion`s) never restores live: `requestRestore` saves the current data as `backups/before-restore.json`, writes `restore-pending.json`, and `migrate` on the next start drops all tables, runs the migrations and inserts the rows (columns present in both, so older backups restore; a failure rolls back, starts empty and stores kv `restoreError`). `runAutoBackup` (startup and foreground, once a day, kv `backupStatus`) always keeps the last 3 copies in `Paths.document/backups` and, with «Автокопия в папку» (`autoBackupEnabled`, folder URI in kv `backupDir`), the last `autoBackupKeep` in that folder; a folder write error shows in Settings. Android Auto Backup is on by default (`allowBackup`, no rules); the WAL is checkpointed when the app goes to the background so the copied `.db` file is complete.
- **History.** The «История» tab (`src/app/(tabs)/history.tsx`) lists algorithms learned (`school` icon, from `learn_log`) and refreshed with flash cards (`albums` icon, from `card_log`) per day for the last `historyDays` days; the day header shows both counts (`getHistory` + `groupHistory`/`formatDayHeader` in `src/logic/history.ts`, pure, tested; fixed Russian weekday/month names, no `Intl`). It only limits what is shown; neither log is ever pruned (streak, charts, forecast and budget read `learn_log`).
- **Forecast.** The dashboard's «Прогноз» card uses `forecastFinish` (`src/logic/forecast.ts`, pure, tested): when every algorithm is learned at the last 14 days' pace of new algorithms (marks never expire; with a single goal there is no fixed number of new ones a day).
- **Code viewer.** `src/components/CodeViewer.tsx` tokenizes with `prism-react-renderer` (vsDark/vsLight themes) into RN `<Text>`. Zoom changes `fontSize` (pinch or +/-) rather than scaling, and is persisted as `codeFontSize`. Inside markdown, `MarkdownView`'s `fence` rule renders ` ```ts `/`js` fences with `CodeBlock` (same themes, static, scrolls sideways); other fences stay plain. Both render prism's empty lines (a `"\n"` token) as a single space, otherwise RN draws each blank line twice.

- **Custom solutions.** The user can paste their own solution per algorithm (`src/app/solution-editor/[slug].tsx`, table `custom_solutions`, DB v2). On save it is normalized and formatted with `prettier/standalone` + the TypeScript plugin (`src/logic/format-code.ts`), which runs inside the app. If parsing fails, the user may save the code as-is. The Решение tab switches between Моё and Эталон, and the bundled solution is never overwritten.
- **Notes.** The «Заметки» tab (`src/app/algo/[slug]/notes.tsx`, last) holds the user's own Markdown notes per algorithm (table `notes`, DB v8; several per slug, optional title, newest first), e.g. an explanation pasted from Claude or ChatGPT. «Из буфера» opens the editor (`src/app/note-editor/[slug].tsx`, param `id` to edit, `paste=1` prefilled from the clipboard) with a Правка/Просмотр toggle; the list renders each note with `MarkdownView scroll={false}`. Backups include them automatically (every table) and the restore summary counts them.

## Content conventions

Each algorithm JSON has `leetcodeId` (LeetCode problem number, shown as "88. Title"), `conditionMd` (original English from LeetCode; it is overwritten by `content:sync`), `descriptionRuMd` (Russian translation), `solutionTs` (TypeScript with inline **Russian** comments), `ideaRuMd` (solution idea in Russian) and `theory.topicKey`, which points to a shared Russian theory note. The four generated fields are optional, but an algorithm has either all of them or none; tabs without content show a placeholder. Generated content lives in batch modules `scripts/content/generated/*.mjs` (the source of truth; `apply.mjs` documents the contract: per-test `argTypes`/`resultType` for lists/trees, `inPlace`, `sortResult`, plus `cls` for design classes and `prelude`/`harness` for custom `_Node`s or answers with several valid forms). Re-running every batch is a full regression check. `content:sync` preserves generated fields, takes `theory.titleRu` from the theory note, and bumps `seedVersion` only when topics or algorithms change (`contentHash`). `scripts/mock/write-mock.js` produced the single mock algorithm (`merge-sorted-array`).

The «Разбор» tab (`src/app/algo/[slug]/explanation.tsx`, between Решение and Теория) shows the optional `explanationRuMd`: a thorough Russian walkthrough with fixed `##` sections (Задача простыми словами, Наивный подход, Ключевое наблюдение, Техники, Разбор кода, Трассировка, Почему это работает, Пограничные случаи, Сложность, Типичные ошибки, Как узнать такую задачу). It is independent of the all-or-none generated fields. Sources are plain `scripts/content/explanations/<batch>/<slug>.md` files merged by `content:explain`, which requires ≥ 1500 chars of Russian and warns when a ` ```ts ` fence isn't an exact (whitespace-insensitive) excerpt of `solutionTs`; illustrative code that isn't from the solution is fenced ` ```ts naive `. All 150 algorithms have one (batches mirror `generated/`); `00-pilot` is the style reference.

## Rules

- Never commit or push without asking the user first.
